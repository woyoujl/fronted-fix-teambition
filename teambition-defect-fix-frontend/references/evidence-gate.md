# 证据门禁：硬修 / 建议 / 等待

不要求硬修。无法保证修复质量时，优先分析与 Teambition 回填。

## 可硬修（Fix）

同时满足：

1. 已通过 `$teambition-query-defects`，确认为前端 Bug
2. 能复现，或有等价可靠证据（截图 + 明确步骤 + 可定位代码）
3. 期望结果明确（来自 TB 描述、钉钉文档、设计稿、YApi 或用户确认）
4. 改动范围可限制在前端最小路径
5. 本地具备验证手段（测试或浏览器）。若需登录，用户已提供测试账号/密码或等价已登录会话（见 `test-credentials.md`）；否则不得在未说明验证缺口的情况下当 Fix 交付

## 只给建议（Suggest）

出现任一情况，默认不改代码（除非用户明确要求试探性改动）：

- 更像后端/数据/权限源/部署问题，前端只能做展示层兜底讨论
- 根因有多种合理解释，无法用现有证据区分
- 能修但风险高（公共组件、全局样式、鉴权、路由守卫），需要产品/负责人拍板
- 环境缺账号/数据，用户不愿或无法提供测试密码，无法验证，只能给排查建议

## 等待补证（Wait）

出现任一情况，停止改代码，Teambition 回填缺证评论：

- 无复现步骤且无截图/录屏/日志
- 期望结果缺失或与截图/文档冲突
- 钉钉文档有链接且验收依赖该文档，但读不到（无 MCP/无权限/登录墙）→ **提示用户、跳过本单（Wait）、最终总结提醒**（见 `dingtalk-docs.md`）
- 账号、密码、环境、feature flag、灰度条件未知（已按 `test-credentials.md` 提示用户仍未提供）
- 描述自相矛盾，无法选定验收标准
- 设计期望仅依赖蓝湖且 MCP 不可用、同时 TB 也无可用截图/描述

回填「需要补充」中必须可勾选相关项（测试账号、钉钉正文等）。禁止编造验收标准后硬改。

## 会话 / tick 总结（强制）

凡本轮出现「因钉钉文档跳过」的单，最终报告必须单独一节：

```text
## 需用户处理（钉钉文档）
- taskId / 标题：...
  链接：...
  原因：...
  请：粘贴关键正文或开通权限后告知二次修改
```

批量/轮询空跑或有修复时都要带上未清的钉钉阻塞列表（若有）。

## 二次修改入口

当评论区、附件或钉钉文档出现新增证据时：

1. 再次 `$teambition-query-defects` 确认同一 `taskId`
2. 读取新增评论 / `RenderTaskRtfV3` / 文档 / 截图
3. 重新做 Outcome Triage，不沿用上次猜测
4. 进入 Fix 或继续 Wait/Suggest

## 与交付的关系

| 结局 | 改代码 | 当前分支提交 | TB 回填 |
| --- | --- | --- | --- |
| Fix + 验证通过 | 是 | 是（默认不开 MR） | 已修复模板 |
| Fix + 验证失败 | 是（临时）→ **必须自动回滚到修改前** | 否 | 失败证据 + 已回滚 |
| Suggest | 否 | 否 | 建议模板 |
| Wait | 否 | 否 | 暂不硬修模板 |
