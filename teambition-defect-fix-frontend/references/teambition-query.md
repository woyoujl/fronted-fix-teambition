# Teambition 查询门禁集成契约

`$teambition-query-defects` 是 Bug 单查询的唯一流程事实源。本文件只定义查询结果如何放行到 `$teambition-defect-fix-frontend`。

## 调用时机

读取缺陷相关源码、制定修复方案或改代码前，先调用 `$teambition-query-defects`。传入：

- `projectId`
- 负责人姓名、`userId` 或明确任务 ID
- 完成状态、关键词、时间范围等条件

## 放行输入

区分“已确认 Bug 单”与“待核验候选”。进入修复流程的任务至少含：

| 字段 | 要求 |
| --- | --- |
| 项目 | 与指定项目一致 |
| 任务 ID | 唯一，可用于详情/评论 |
| 标题 | 已从详情核验 |
| 负责人 | 姓名与 `userId` 已核验 |
| 任务类型 | `Bug` 或 `缺陷` |
| 状态 | 已读，符合查询范围 |
| 优先级、更新时间 | 接口提供时保留 |
| 备注/上下文 | 足以判断前端范围与是否缺证 |

放行后修复 skill 还应尽快抽取：钉钉/原型链接、设计稿链接、YApi/接口线索、截图附件、评论中的补证。

## 放行条件

1. 来自真实 Teambition 任务 MCP，不是文档 MCP。
2. 项目、负责人、Bug/缺陷类型均已核验。
3. 用户已选定单一缺陷；或已明确列出批量 ID。
4. 足以分类为前端 / 非前端 / 不确定。
5. 目标为前端；不确定时先反馈证据缺口。

## 阻断条件

- 查询 skill 或任务 MCP 不可用
- 仅候选 ID，无法核验标题/负责人/类型
- 人员、缺陷或多项目范围无法唯一确定
- 非 Bug/缺陷，或已确认非前端
- 修改分支不明确（报告当前分支后等待确认）

## 责任边界

| Skill | 负责 | 不负责 |
| --- | --- | --- |
| `$teambition-query-defects` | 只读查询、身份/类型核验、摘要 | 改代码、开 MR、写回填（除非用户只要查询） |
| `$teambition-defect-fix-frontend` | 证据门禁、修复、验证、当前分支提交（默认不开 MR）、TB 回填、可选轮询 | 重写查询算法 |

任一 skill 都不得在用户未明确要求时关闭、归档或流转 Teambition 任务。

## 二次修改衔接

上次为 Wait/Suggest 且 TB 出现新证据时：修复 skill 必须再次调用本查询门禁确认同一 `taskId`，再进入证据读取，不得跳过查询直接改代码。
