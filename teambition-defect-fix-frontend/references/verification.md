# 修复后验证

代码改完必须验证。未验证不得声称已修复，不得默认流转 Teambition，也不得在 MR 中写“已自动验证通过”。

## 验证顺序

1. **账号与环境门禁**：若页面需登录/角色/特定数据，先按 `test-credentials.md` 向用户索取测试账号、密码、启动方式与测试数据；未提供则不得声称浏览器验证通过。
2. **静态 / 聚焦测试**：项目已有最小相关测试、lint、typecheck 或构建命令。优先 package script / 单测路径。
3. **浏览器自动验证**：页面可见、可交互、路由、样式、状态同步类缺陷必须做。
4. **UI 截图对比**：UI/样式/布局类额外执行 `ui-replay.md`。
5. **结果归档**：命令、退出码、浏览器结论、截图路径写入最终报告与 TB 回填（可写测试用户名，**禁止写密码**）。

## 浏览器验证（Cursor）

优先使用 `cursor-ide-browser`：

1. 确认本地服务已启动，或按用户/README 提供的命令启动最小环境。
2. 需要登录时：用用户当次提供的测试账号密码完成登录（仅会话内使用），再进入缺陷页。
3. `browser_tabs` 查看已有标签；需要时 `browser_navigate` 打开缺陷页。
4. 对已有标签先 `browser_lock`（action: lock），再交互。
5. 按复现步骤：`browser_click` / `browser_type` / `browser_fill` / `browser_press_key` / `browser_scroll`。
6. `browser_snapshot` 核对文案、控件状态、错误提示、列表数据。
7. 需要视觉证据时 `browser_take_screenshot`（避免把密码打在可读截图里）。
8. 必要时 `browser_cdp` + `Runtime.evaluate` / network 线索核对请求与展示。
9. 全部浏览器操作结束后 `browser_lock`（action: unlock）；可退出登录。

其他环境可用 chrome-devtools 等价能力，但步骤目标相同：账号就绪 → 导航 → 复现 → 断言 → 截图。

## 通过 / 失败 / 阻塞

**通过**：复现步骤下实际结果与期望一致，相关测试通过，无明显回归。

**失败**：原问题仍在、引入新报错、测试失败、或只能部分复现。失败时必须按 `gitlab-mr.md` **自动回滚到该单修改前**，不得把失败 diff 留在当前分支。

**阻塞**：起不来、用户未提供测试账号/密码、缺权限/数据、浏览器工具不可用。报告阻塞原因与手工路径，不假装已自动验证；缺账号时走 `evidence-gate` Wait。若已改过代码，同样回滚到修改前再 Wait/回填。

## 交付门禁

| 验证结果 | GitLab | Teambition 回填 | 状态流转 |
| --- | --- | --- | --- |
| 通过 | 当前分支 commit（默认不开 MR） | 原因/改动/验证/风险/SHA | 仅目标状态明确且用户或流程要求时 |
| 失败 | **必须自动回滚到该单修改前**；不提交「已修复」 | 失败证据 + 已回滚说明 | 不标已修复 |
| 阻塞 / 证据不足 | 不提交修复；若已改过代码同样回滚到修改前 | 缺证与建议（含缺测试账号） | 不标已修复 |

## 禁止

- 删测试、降断言、跳过核心校验
- 只用“代码看起来对”代替运行验证
- 浏览器未执行却写“已自动验证通过”
- 在回填/MR/报告中写测试密码
- 未获账号时假装已登录验证
- 验证失败却不自动回滚到修改前
